## 1. Схема распределения памяти (Stack -> Heap) в Sandbox.Memory

    STACK (стек потока)                        HEAP (управляемая куча)
    [s: CommitRecordStruct]
      FilesCount = 3 (в стеке)
      Hash = 0x1001 -------------------------> string "a1b2c3"

    [c: CommitRecordClass]
      ссылка = 0x2001 -----------------------> [объект CommitRecordClass]
                                                 FilesCount = 3
                                                 Hash = 0x1001 --> string "a1b2c3"

    Вызов ChangeStructField(s):
    [item: CommitRecordStruct] (полная копия s в стеке; изменение item.FilesCount не затрагивает s)

    Вызов ChangeClassField(c):
    [item: ссылка = 0x2001] -----------------> тот же самый [объект CommitRecordClass]
                                               (изменение item.FilesCount меняет исходный объект)

## 3. Теоретические пояснения

### Передача ссылочного типа по значению vs через ref
- По значению (`ChangeClassField(CommitRecordClass item)`): передаётся копия ссылки на объект в куче. Изменение полей объекта (`item.FilesCount = 10`) сохраняется снаружи, потому что обе ссылки указывают на один объект. Переприсваивание (`item = new ...`) меняет только локальную копию ссылки внутри метода, а исходная переменная остаётся указывать на старый объект.
- С модификатором `ref` (`ReplaceClassRef(ref CommitRecordClass item)`): метод получает доступ к самой переменной вызывающего кода, поэтому `item = new ...` подменяет ссылку у оригинала.

### Почему Span<T> не может быть полем обычного класса (class)
`Span<T>` является `ref struct` и обязан размещаться строго на стеке потока. Экземпляры обычных классов всегда хранятся в управляемой куче (Heap) и управляются сборщиком мусора. Если бы `Span<T>` разрешили хранить в поле класса, срез мог бы пережить буфер на стеке, на который он ссылается, а также сломать потокобезопасность из-за неатомарного обновления пары «указатель + длина».
